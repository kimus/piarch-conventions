From the supplied idea and living specs, produce a TECHNICAL proposal document. Return the entire Markdown document, without narration or fences. Begin with an H1 title in the reader's words: it is what listings show.

Required sections: ## Why, ## Goals, ## Scope / Non-goals, ## Capabilities, ## Stack, ## Compatibility, ## Verification Strategy, ## Open Questions. Include ## Use Cases, ## Technical Approach, and ## Security / Failure Modes only when they carry content a reader needs; where one does not apply, replace the section with one line stating why it is omitted rather than filling it. State each section in the shortest form that stays reviewable: a line is enough where a line is honest.

Under ## Capabilities, list the capability branches this proposal creates or grows, one bullet each, with what each makes usable. A capability is a functional area with its own living specification; a deliverable is a slice of one capability, never a slice of the whole initiative. Under ## Stack, name the language, runtime, storage, and principal libraries with the reason each is chosen and what was rejected; these recorded words also select the conditional rule sets supplied to later turns, so name technologies plainly (sqlite, deployment, migration, release) instead of describing them away. Under ## Compatibility, state what state or interface exists outside the working copy that the project does not control and what a change may break; an empty statement is a claim that nothing is exposed, so verify it instead of assuming it, and keep the verified claim to one line plus the date it was checked. Where backup, deployment, migration, or release work applies, name that topic in Stack or Compatibility so its rules are supplied; if it applies and the rules are absent, ask before drafting.

Specify proportionate architecture, dependencies/environment, data/control flow, tradeoffs, failure/recovery, and trust boundaries. Keep simple projects simple; mark irrelevant concerns with reasons. Use the provenance tags from the system writing rules for assumptions and unknowns instead of narrating how a claim came to be believed. Detailed normative requirements belong in a capability delta, and acceptance criteria in a deliverable contract, not the proposal. Under ## Open Questions, list each genuinely unresolved question as one bullet with its owner, or write exactly `- none`; never leave the section empty. Do not manufacture open questions for settled decisions, and remember that every question you list blocks the node's gate: the gate passes only when the section declares an honest `- none`, so resolve a question into a recorded decision while drafting rather than carrying it to the gate.
